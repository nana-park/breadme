# 데스크톱·모바일 반응형 전략

## 이 문서의 목적

채용 담당자가 어떤 화면으로 방문해도 같은 사람, 같은 프로젝트, 같은 연락 경로를 찾을 수 있게 합니다. 데스크톱에서는 내용을 빠르게 훑어보고, 모바일에서는 위에서 아래로 읽어도 빠지는 정보가 없어야 합니다.

이번 작업은 **Home의 React 미리보기 뼈대**입니다. 기존 포트폴리오 전체를 옮기거나 최종 디자인을 확정하는 단계가 아닙니다. 프로젝트와 연락 영역의 준비 상태는 화면에 표시하며, 실제 내용이 준비된 것처럼 성과나 연락처를 만들어 넣지 않습니다.

기존 상세 내용을 확인하는 외부 링크는 원본 `index.html`의 메타데이터에 있는 [공개 포트폴리오](https://nana-park.github.io/Portfolio/)를 사용합니다.

## 1. 모든 화면에서 유지할 것

- 이름과 원본 소개 문구, 섹션 순서, 목적지와 핵심 기능을 유지합니다.
- 하나의 React 컴포넌트와 하나의 콘텐츠 원본을 사용합니다. 모바일용 페이지나 콘텐츠 복사본을 만들지 않습니다.
- 문서 안의 요소 순서와 눈으로 읽는 순서를 맞춥니다. CSS로 중요한 내용을 뒤로 보내지 않습니다.
- 마우스를 올렸을 때만 나타나는 설명이나 버튼을 만들지 않습니다.
- 모바일에서도 핵심 정보를 숨기거나 가로 슬라이드 안에 넣지 않습니다.
- `소개 → 프로젝트 → 연락` 순서로 직접 읽거나 메뉴로 이동할 수 있게 합니다.

### 화면별 읽기 방식

| 방문 상황 | 배치 원칙 | 같아야 하는 정보와 행동 |
| --- | --- | --- |
| 데스크톱에서 빠르게 확인 | 넉넉한 읽기 폭과 명확한 제목으로 구역을 구분합니다. 여유 공간이 있을 때만 나란히 배치합니다. | 이름·포지셔닝 확인, 프로젝트 영역 이동, 기존 상세 정보와 연락 경로 찾기 |
| 태블릿에서 탐색 | 여백과 열 수를 줄여 글과 조작 영역이 비좁아지지 않게 합니다. | 데스크톱과 같은 내용과 목적지 |
| 모바일에서 차례로 읽기 | 한 열을 기본으로 합니다. 제목, 설명, 행동의 순서를 유지하고 메뉴는 펼쳐서 사용합니다. | 내용을 생략하지 않고 동일한 정보와 경로 제공 |

화면이 작다는 이유로 요약의 의미를 바꾸지 않습니다. 추후 프로젝트 요약을 줄여야 한다면 모든 화면에 사용할 원문을 먼저 검토합니다.

## 2. 콘텐츠 우선순위

1. **누구인지:** `Nahyun Park`와 원본 Hero 문구를 보여 줍니다.
2. **무엇을 하는지:** 원본의 `Designing Actionable AI`, `AI PRODUCT MANAGER · UX RESEARCH · PSYCHOLOGY`를 그대로 유지합니다.
3. **어떤 일을 했는지:** 이번에는 프로젝트 콘텐츠 준비 상태와 기존 포트폴리오로 이동하는 경로를 보여 줍니다. 실제 프로젝트명, 역할, 기간과 성과는 원본 대조와 검토 후 옮깁니다.
4. **어디서 더 확인하거나 연락할지:** 준비 상태를 명확히 밝히고, 기존 공개 포트폴리오의 실제 상세 정보로 안내합니다. 아직 없는 상세 페이지나 연락 폼처럼 보이게 만들지 않습니다.

한국어 UI와 원본 영어 Hero가 함께 있는 상태입니다. 영어 원문에는 `lang="en"`을 지정합니다. 이는 영어판 출시나 번역 승인으로 보지 않습니다. 영어 UI가 승인되기 전에는 언어 전환 버튼과 자동 대체 번역을 제공하지 않습니다.

이름·소개·링크 등 내용은 `src/content/`, 반복 메뉴·버튼 문구는 `src/locales/ko/`, 내비게이션의 목적지와 동작 설정은 `src/config/`에서 관리합니다. 화면 코드에 같은 문구를 반복해 넣지 않습니다.

## 3. 화면 너비 기준

[기존 CSS 규칙](ground-rules/08-css-and-responsive-styles.md)을 그대로 따릅니다. 너비는 기기 모델명이 아닌 브라우저 표시 영역의 CSS 픽셀 기준입니다.

| 구간 | 너비 | 스타일 적용 |
| --- | --- | --- |
| 데스크톱 | 1025px 이상 | CSS Module의 기본 스타일 |
| 태블릿 | 768px–1024px | `max-width: 1024px`에서 필요한 부분만 변경 |
| 모바일 | 767px 이하 | `max-width: 767px`에서 필요한 부분만 변경 |

CSS Module 안에서는 기본 → 태블릿 → 모바일 순서로 씁니다. 화면 너비를 JavaScript로 읽어 콘텐츠 자체를 바꾸지 않습니다. 메뉴 상태를 정리하기 위한 화면 변경 감지는 콘텐츠 분리와 구분합니다.

- 넓은 화면에서도 본문이 끝없이 길어지지 않도록 최대 읽기 폭을 둡니다.
- 제목은 자연스럽게 줄바꿈하고 고정 높이에 가두지 않습니다.
- 긴 URL이나 단어, Grid·Flex의 자식이 화면 밖으로 밀려나지 않게 합니다.
- 320px에서도 페이지 전체를 좌우로 움직이지 않고 읽고 조작할 수 있어야 합니다.
- 화면을 넘치는 내용을 단순히 잘라서 결함을 감추지 않습니다.

## 4. 메뉴와 이동

### 공통

- 소개·프로젝트·연락은 같은 Home 안의 실제 영역으로 이동하는 `<a href="#…">` 링크입니다.
- 링크 이동과 새로고침, 주소의 해시, 브라우저 뒤로·앞으로 동작은 브라우저 기본 기능을 사용합니다.
- 지금은 별도 라우터, 가상 상세 페이지, 백엔드를 도입하지 않습니다.
- 본문 바로가기 링크와 제목 위계를 제공합니다. 메뉴와 본문 모두 키보드로 도달할 수 있어야 합니다.
- 메뉴나 고정 요소가 이동한 제목과 키보드 초점을 가리지 않는지 확인합니다.

### 모바일 메뉴

메뉴는 버튼으로 펼치고 접는 일반 내비게이션입니다. 대화상자처럼 화면과 키보드를 가두는 방식은 사용하지 않습니다.

- 버튼의 이름과 `aria-expanded`, `aria-controls`로 메뉴 상태와 연결 대상을 전달합니다.
- 닫혀 있는 링크는 보이지 않으며 키보드 탐색 순서에서도 빠집니다.
- 열었을 때 Tab으로 메뉴 항목을 차례로 이용하고, 그 뒤 본문으로 이동할 수 있어야 합니다.
- Escape로 닫으면 초점이 메뉴 버튼으로 돌아옵니다.
- 항목을 선택하면 메뉴가 닫히고 해당 영역으로 이동합니다. 이동 후 다음 키보드 탐색이 자연스러운지 확인합니다.
- 메뉴를 연 상태에서 태블릿·데스크톱으로 바꿨다가 모바일로 돌아와도 숨은 메뉴의 상태나 초점이 남지 않아야 합니다.
- 반복해서 열고 닫거나 빠르게 너비를 바꿔도 링크를 사용할 수 있어야 합니다.

## 5. 읽기와 조작 접근성

- 주요 버튼과 독립 링크의 조작 영역은 최소 **44×44 CSS px**로 잡습니다.
- 글자 확대 200%에서 내용이나 기능이 사라지지 않아야 합니다. 화면 확대와 좁은 화면 테스트를 서로 대신하지 않고 각각 확인합니다.
- 제목 단계는 `h1 → h2 → h3`로 의미 있게 이어집니다. 글자 크기만으로 제목을 흉내 내지 않습니다.
- 링크·버튼은 색상만으로 구분하지 않으며, 키보드 초점은 또렷하게 보여야 합니다.
- 일반 텍스트 대비는 4.5:1, 큰 텍스트는 3:1 이상을 검토 기준으로 사용합니다. 실제 색상 조합을 검사하기 전에는 통과했다고 기록하지 않습니다.
- 기본 콘텐츠 확인에 애니메이션이 필요하지 않아야 합니다. `prefers-reduced-motion` 설정에서는 불필요한 이동과 부드러운 스크롤을 줄이거나 끕니다.
- 새 창이 꼭 필요하지 않은 링크는 현재 창에서 엽니다. 새 창을 사용한다면 방문자에게 미리 알립니다.

## 6. 이미지와 성능: 실제 콘텐츠를 옮길 때의 기준

이번 뼈대에는 원본의 무거운 이미지·영상이나 외부 글꼴을 일괄 복사하지 않습니다. 다음 기준은 이미지가 실제로 들어오는 시점에 적용하고 검증합니다.

- 이미지가 전달하는 정보에 맞는 대체 텍스트를 작성하고, 장식 이미지는 빈 대체 텍스트를 사용합니다.
- 표시 크기에 맞는 파일과 `srcset`·`sizes`를 사용합니다. 필요한 경우 WebP·AVIF 등 압축 형식을 검토합니다.
- 이미지의 너비·높이 또는 비율을 미리 확보해 로딩 중 주변 내용이 밀리지 않게 합니다.
- 첫 화면의 핵심 이미지는 불필요하게 지연 로딩하지 않습니다. 아래쪽 이미지는 필요할 때 읽어옵니다.
- 중요한 문구를 이미지 속에만 넣지 않습니다. 모바일용 잘라내기가 필수 내용을 없애지 않는지 확인합니다.
- 자동 재생 영상, 대형 애니메이션, 외부 분석·추적 스크립트는 기본 구조에 추가하지 않습니다.
- 이미지·글꼴·서비스를 추가한 뒤에는 실제 전송 크기와 로딩, 레이아웃 이동을 다시 측정합니다. 측정하지 않은 성능 점수나 개선 수치는 제시하지 않습니다.

## 7. 자체 QA 확인표

아래 표는 **실행할 검사와 판정 기준**입니다. 이 문서만으로 테스트 통과를 의미하지 않습니다. 실제 실행 결과, 브라우저, 재현 방법과 남은 한계는 PR의 테스트 항목과 별도 QA 기록에 남깁니다.

### 화면 크기

| 표시 영역 너비 | 특히 확인할 사항 |
| --- | --- |
| 320px | 전체 가로 넘침 없음, 긴 Hero 문구 줄바꿈, 메뉴·링크 44px 조작 영역, 필수 정보 유지 |
| 390px | 기본 모바일 읽기 순서, 펼침 메뉴, 프로젝트와 연락까지 끊기지 않는 탐색 |
| 767px | 모바일 마지막 구간의 메뉴 표시와 줄바꿈 |
| 768px | 태블릿 첫 구간의 메뉴 전환, 빠진 링크·중복 링크·남은 펼침 상태 없음 |
| 1024px | 태블릿 마지막 구간의 읽기 폭과 열 배치 |
| 1025px | 데스크톱 첫 구간의 레이아웃 전환과 정보 동일성 |
| 1440px | 기본 데스크톱 위계, 최대 읽기 폭, 메뉴·프로젝트·연락 경로 |

### 조작과 접근성

- [ ] 모든 너비에서 소개·프로젝트·연락의 내용과 목적지가 같습니다.
- [ ] 키보드만으로 본문 바로가기, 메뉴, 각 링크를 순서대로 사용할 수 있고 초점이 보입니다.
- [ ] 200% 글자 확대에서 제목·본문·메뉴가 겹치거나 잘리지 않습니다.
- [ ] 320px 재배치와 브라우저 확대에서도 양방향 스크롤 없이 핵심 내용을 읽을 수 있습니다.
- [ ] 모바일 메뉴를 반복해서 열고 닫을 수 있고 Escape가 닫기와 초점 복귀를 수행합니다.
- [ ] 메뉴를 연 채 767px ↔ 768px, 모바일 ↔ 데스크톱으로 변경한 뒤에도 정상적으로 사용할 수 있습니다.
- [ ] 메뉴 선택 후 해당 영역에 도착하고, 뒤로·앞으로·해시 주소 새로고침이 동작합니다.
- [ ] 화면 이동을 줄이는 설정에서 불필요한 애니메이션이 실행되지 않습니다.
- [ ] 숨겨진 항목이 키보드 탐색에 남지 않고, 핵심 기능에 Hover가 필요하지 않습니다.
- [ ] 외부 링크는 실제 원본 목적지로 연결되며 준비 중인 기능을 완료된 것처럼 보이지 않습니다.
- [ ] 브라우저 콘솔의 심각한 오류, 깨진 링크, 실패한 리소스가 없습니다.
- [ ] 코드 검사·타입 검사·테스트·프로덕션 빌드를 실행하고 각각의 결과를 구분해 기록합니다.

자동 검사는 구조와 반복 회귀를 확인하는 보조 수단입니다. 실제 화면의 읽기 흐름, 초점, 확대와 터치 경험까지 확인한 범위를 넘어서 접근성이나 기기 지원을 보장하지 않습니다.
