# 문서 관리와 작은 개선의 반복

[← README](../README.md) · [개선 목록](backlog.md) · [기존 협업 규칙](ground-rules/README.md)

이 문서는 기존 Ground Rules를 대체하지 않습니다. 실제 구현·운영 상태를 찾기 쉽게 연결하고, 변경한 만큼 문서를 갱신하는 방법입니다. 체크리스트는 이번 문서 기반에서 제안하는 운영 양식이며 새로운 서비스·추적 도구·자동 알림을 설치하지 않습니다.

## 1. 어떤 정보가 기준인가

| 정보 | 단일 기준 | 관련 설명 |
| --- | --- | --- |
| 실행·의존성 버전·스크립트 | `package.json`, `package-lock.json`, `.nvmrc` | [운영 안내](engineering/runbook.md) |
| 페이지 ID·배포 HTML 경로 | `src/config/originalRoutes.ts` | [사이트 구조(IA) 및 페이지 명세](product/routes-and-content.md) |
| 현재 문구·콘텐츠·링크 | 행동 목록의 소스 파일 지도 | 제품 문서는 목적·검증 상태를 설명하며 전체 문구를 복제하지 않음 |
| 디자인의 실제 값·연결 | 사용 중인 CSS/컴포넌트 | [디자인 안내](design-system/README.md), [적용표](design-system/component-adoption.md) |
| 작업/병합 권한·예외 절차 | [Ground Rules](ground-rules/README.md) + 해당 작업의 명시적 승인 | 새 문서가 승인 범위를 넓히지 않음 |
| 정확한 코드/공개 상태 | GitHub commit·PR·Actions + 공개 `deployment.json` | 요약은 [버전 허브](../versions/README.md) 한 곳 |
| 검사 결과 | 해당 커밋의 CI/로컬 결과 + 범위가 명시된 QA 보고서 | [QA 안내](qa/README.md) |
| 아직 해결하지 않은 문제 | [backlog](backlog.md) | 중복으로 별도 TODO 목록을 만들지 않음 |
| 지난 변경의 이유 | PR 및 [변경 이력](../versions/CHANGELOG.md) | 장기 설계 결정만 아래 양식으로 해당 주제 문서에 기록 |

문서와 구현이 다르면 조용히 코드에 맞춰 정책을 바꾸지 않습니다. `문서 오류`, `구현 결함`, `아직 적용하지 않은 목표` 중 무엇인지 구분하고 근거를 남깁니다. 공개된 사실과 제품 제안이 충돌하면 소유자의 결정을 받습니다.

## 2. 담당 역할

- 제품 소유자: 공개 주장·개인정보·디자인 방향·새 기능 범위·출시 여부 결정. 현재 저장소 소유자는 `nana-park`이며 별도 담당자나 SLA를 임의로 지정하지 않습니다.
- 변경 작성자: 관련 소스·문서·검사를 같은 PR에서 갱신하고 미검수와 실패를 공개합니다.
- 검토자: 요구사항과 완료 조건, 원본/변경 비교, 공개 권한을 확인합니다. 자동 테스트가 이 역할 전체를 대신하지 않습니다.

혼자 작업해도 이 세 관점을 분리해 확인합니다. 단순 작업마다 새 회의·문서·승인 단계를 만들 필요는 없습니다.

## 3. 변경 종류별 갱신표

| 변경 | 같은 PR에서 확인할 문서 | 검증 |
| --- | --- | --- |
| 문구·주장·자료 링크 | 관련 페이지 README/콘텐츠 원본. 의미 변화면 제품/행동 목록 | 출처·공개 적합성·목적지. 오탈자만이면 README 갱신 불필요 |
| 경로·메뉴·CTA·Coming Soon 전환 | 행동 목록, 페이지 README, 필요 시 제품 여정 | 직접 진입/새로고침/복귀/모바일·키보드 |
| 공통 UI·반응형 | 컴포넌트 적용표, 영향 페이지 README, 해당 디자인 규칙 | 영향 페이지 모바일+데스크톱, 접근성·회귀 |
| 페이지/전체 UI 디버깅 | 같은 브랜치의 QA 보고서. 넓은 범위면 As-is/To-be 스크린샷 | [QA 양식](qa/README.md), 작은 간격 수정마다 별도 대형 보고서는 불필요 |
| 구조·자산·외부 의존성 | 아키텍처, 자산 문서, 운영 안내 | 재현 가능한 준비/빌드·오류 처리 |
| 명령·배포·검사 방식 | 운영 안내와 QA 안내 | 명령 실제 실행·워크플로 트리거 확인 |
| 작업 해결·결정·배포 | backlog, PR, 변경 이력. 실제 공개 후 버전 허브 | 정확한 commit·CI·deployment.json, 완료 조건 |
| 문서만 정리 | 링크·소스 근거·상태/날짜·중복 진실 확인 | 코드 불변 확인, 실행한 검사와 하지 않은 검사 분리 |

## 4. 작업 종료 체크리스트

1. 변경 목표와 완료 조건을 한 문장으로 설명할 수 있는가?
2. 실제 구현과 제안/보류를 섞지 않았는가? 공개 자료 없는 내용을 넣지 않았는가?
3. 소스 원본 위치가 바뀌면 링크·페이지 README·적용표가 함께 바뀌었는가?
4. 결과에 `통과 / 실패 / 미실행 / 환경 제한`과 정확한 커밋·범위를 적었는가?
5. 관련 backlog는 해결 증거와 함께 닫거나 남은 이유를 갱신했는가?
6. 다른 문서의 현재 상태와 모순되지 않는가? 과거 보고서는 삭제하지 않고 당시 시점임을 표시했는가?
7. `git diff --check`와 변경 파일 목록을 확인했는가? 빌드 산출물·개인 자료·비밀정보가 없는가?
8. PR 작성/테스트 성공/병합/배포를 서로 다른 상태로 보고했는가?

정기 날짜마다 문서를 전부 다시 쓰기보다는 **동작이 바뀌는 PR**과 **공개 직전**에 갱신합니다. 변하지 않은 문서를 읽었다는 이유만으로 수정 날짜를 올리지 않습니다.

## 5. 필요한 때만 남기는 결정 기록

폴더 이동, 새 외부 서비스, 번역/자료 제공 방식처럼 다음 작성자가 다시 고민할 결정만 해당 주제 문서에 기록하고 PR에서 연결합니다. 사소한 수정은 PR 설명으로 충분합니다.

```text
결정: 짧은 제목
상태: 제안 / 승인 / 적용 / 대체됨
관련 문제: backlog ID 또는 issue/PR
이유와 근거: 사용자 문제·코드/검사 링크
검토한 선택: 선택지와 중요한 비용/위험
결정 내용: 승인된 범위, 아직 하지 않는 일
승인/적용 근거: 날짜·PR·커밋 (없으면 미승인/미적용)
다시 볼 조건: 어떤 변화가 생기면 재검토하는가
```

승인 전 제안을 승인된 디자인 예외 목록에 넣지 않습니다. 기존 [디자인 예외 절차](ground-rules/09-design-system-governance.md)와 [콘텐츠/언어 규칙](ground-rules/10-content-and-localization.md)을 따릅니다.
