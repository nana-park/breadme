# 코드 구조와 주석 규칙

## 목표

이 프로젝트의 코드는 개발자만 이해하는 구현물이 아니라, 기획자도 페이지 구조와 의사결정의 이유를 추적할 수 있는 문서 역할을 해야 합니다.

주석은 코드의 **무엇(WHAT)**과 **왜(WHY)**를 모두 설명합니다. WHAT은 페이지와 주요 섹션의 역할을 빠르게 파악하게 하고, WHY는 구현 결정, 제약과 예외의 이유를 추적하게 합니다.

단, 모든 코드 줄에 WHAT과 WHY를 반복하지 않습니다. WHAT은 페이지·주요 섹션·복잡한 기능 단위에 작성하고, WHY는 코드만 읽어서는 알 수 없는 결정이 있을 때 해당 코드 가까이에 작성합니다.

## 언어별 주석 문법

`#`은 Markdown 제목이나 일부 언어에서 사용합니다. React 프로젝트에서는 파일 종류에 따라 문법이 다릅니다.

```jsx
// JavaScript 한 줄 주석

/* JavaScript 여러 줄 주석 */

{/* JSX 화면 구조 안의 주석 */}
```

```css
/* CSS 주석 */
```

```md
# Markdown 대제목
## Markdown 중제목
### Markdown 소제목
```

## WHAT과 WHY의 2단계 주석 체계

### 1단계 — 구조 주석: `WHAT`

페이지와 주요 섹션이 무엇을 담당하는지 설명합니다. 기획자가 파일을 열었을 때 화면 구조를 목차처럼 읽을 수 있어야 합니다.

```jsx
{/*
 * 01. Hero Section
 * WHAT: 방문자에게 이름, 직무와 핵심 포지셔닝을 처음 전달하는 영역
 */}
<HeroSection />
```

### 2단계 — 결정 주석: `WHY`

코드만으로 알 수 없는 기획·디자인·기술 결정의 이유를 설명합니다.

```js
// WHY: 현재 필터를 공유하고 새로고침 후에도 유지하기 위해 URL query에 저장한다.
```

같은 위치에서 WHAT과 WHY가 모두 중요하면 하나의 주석 블록에 함께 작성합니다.

```jsx
{/*
 * 03. Featured Projects
 * WHAT: 대표 프로젝트를 성과와 역할 중심으로 소개하는 영역
 * WHY: 전체 프로젝트보다 채용 담당자의 빠른 탐색을 우선해 3개만 노출한다.
 */}
<FeaturedProjectsSection />
```

필요한 경우 다음 항목을 추가할 수 있습니다.

```text
WHAT: 무엇을 담당하는가
WHY: 왜 이 방식과 구성을 선택했는가
DESIGN: 어떤 디자인 시스템 규칙 또는 예외를 적용했는가
REVIEW: 기획자와 다시 확인해야 하는 조건은 무엇인가
```

- 페이지와 주요 섹션에는 `WHAT`을 기본으로 작성합니다.
- 자명하지 않은 구현 결정, 제약과 예외에는 `WHY`를 작성합니다.
- 단순한 버튼 클릭이나 변수 할당처럼 코드 자체로 명확한 줄에는 반복 설명을 붙이지 않습니다.
- HOW, 즉 구체적으로 어떻게 동작하는지는 코드와 명확한 함수·컴포넌트 이름으로 표현합니다.

## 페이지와 섹션 위계

각 페이지는 다음 위계를 유지합니다.

```text
Page
├─ Major Section
│  ├─ Section Header
│  ├─ Content Group
│  └─ Supporting UI
└─ Major Section
```

페이지 파일의 렌더링 순서가 실제 화면의 섹션 순서와 같아야 합니다.

```jsx
export function HomePage() {
  return (
    <PageLayout>
      {/* 01. Hero — WHAT: 이름, 직무와 핵심 포지셔닝 전달 */}
      <HeroSection />

      {/* 02. Partners — WHAT: 신뢰를 뒷받침하는 주요 협업사 소개 */}
      <PartnersSection />

      {/* 03. History — WHAT: 경력과 성장 과정을 시간순으로 설명 */}
      <HistorySection />

      {/* 04. Vision — WHAT: 앞으로 만들고 싶은 제품과 방향 제시 */}
      <VisionSection />
    </PageLayout>
  );
}
```

- 대제목은 페이지 또는 주요 섹션을 표현합니다.
- 중제목은 섹션 안의 콘텐츠 그룹을 표현합니다.
- 소제목은 카드나 세부 항목을 표현합니다.
- 시각적인 글자 크기만으로 위계를 만들지 않고 HTML heading도 `h1` → `h2` → `h3` 순서를 지킵니다.
- 섹션 이름은 기획 문서, 컴포넌트 이름과 코드 주석에서 동일하게 사용합니다.

## 파일 내부 구분

긴 파일은 다음 순서를 기본으로 합니다.

```text
1. imports
2. constants and configuration
3. component
4. state and derived values
5. event handlers
6. render
7. helper components, if truly local
```

큰 구역만 눈에 잘 띄는 주석으로 나눕니다.

```js
// =============================================================================
// Project filters
// =============================================================================
```

작은 코드마다 설명 주석을 붙여 시야를 방해하지 않습니다. 파일이 주석 없이는 이해하기 어렵다면 먼저 함수나 컴포넌트를 분리하고 이름을 개선합니다.

## 표준 주석 표식

검색과 협업이 쉽도록 아래 표식을 통일해서 사용합니다.

### `DECISION`

기획 또는 기술 선택의 이유를 기록합니다.

```js
// DECISION: GitHub Pages 새로고침 오류를 피하기 위해 HashRouter를 사용한다.
```

### `DESIGN-EXCEPTION`

디자인 시스템을 따르지 않는 의도적인 예외를 표시합니다. 반드시 적용 범위, 이유와 향후 처리 방향을 함께 씁니다.

```css
/*
 * DESIGN-EXCEPTION [home-hero]:
 * Home의 첫 화면만 캠페인 비주얼을 강조하기 위해 기본 container 폭을 사용하지 않는다.
 * 이 규칙은 다른 페이지로 확장하지 않는다.
 * 재검토 조건: Hero 디자인이 교체될 때.
 */
```

예외를 단순히 `!important`로 숨기지 않습니다. `!important`가 꼭 필요하면 같은 위치에 이유를 기록합니다.

### `CONTENT-REVIEW`

기획자 확인이 필요한 문구나 데이터를 표시합니다.

```jsx
{/* CONTENT-REVIEW: 프로젝트 성과 수치는 최종 이력서와 대조 필요 */}
```

### `TODO`

이미 범위와 완료 조건이 정해진 후속 작업만 기록합니다.

```js
// TODO: 모바일 메뉴가 열린 동안 body 스크롤을 잠근다.
```

막연한 아이디어는 코드 TODO가 아니라 이슈나 기획 문서에 기록합니다.

### `FIXME`

현재 동작하지만 결함이나 위험이 있어 반드시 수정해야 하는 부분에 사용합니다.

```js
// FIXME: 빠른 필터 전환 시 이전 이미지 요청 결과가 덮어쓸 수 있다.
```

### `ACCESSIBILITY`

의도적인 접근성 처리나 추가 검토가 필요한 부분을 표시합니다.

```jsx
{/* ACCESSIBILITY: 장식 이미지이므로 빈 alt를 사용한다. */}
```

## 디자인 시스템과 예외 관리

- 색상, 간격, 글자 크기와 모서리 값은 디자인 토큰을 우선 사용합니다.
- 토큰에 없는 숫자를 바로 입력하기 전에 기존 토큰으로 해결할 수 있는지 확인합니다.
- 디자인 시스템을 벗어난 값이 의도적이면 `DESIGN-EXCEPTION`을 남깁니다.
- 반복되는 예외는 더 이상 예외로 두지 않고 디자인 토큰 또는 컴포넌트 variant로 승격할지 검토합니다.
- 컴포넌트 variant는 의미가 드러나는 이름을 사용합니다.

```jsx
<ProjectCard variant="featured" />
```

```jsx
// 비권장: 의미를 알 수 없는 시각 값 전달
<ProjectCard width="720px" orange large />
```

## 기획자와 개발자가 함께 읽기 위한 코드 기준

### 화면 이름 통일

내비게이션, 라우트, 페이지 파일과 기획 문서에서 같은 이름을 사용합니다.

```text
기획: Projects
라우트: /projects
페이지: ProjectsPage.jsx
폴더: pages/projects/
```

### 콘텐츠와 화면 코드 분리

프로젝트명, 설명, 날짜, 태그처럼 자주 바뀌는 정보는 가능하면 `src/content/`에 둡니다. 콘텐츠를 바꾸기 위해 레이아웃 코드를 수정하지 않게 합니다.

### 상태를 빠뜨리지 않기

데이터 또는 사용자 입력이 있는 기능은 다음 상태를 명시적으로 검토합니다.

- 기본 상태
- 로딩 상태
- 데이터 없음
- 오류 상태
- 성공 상태
- 비활성 상태

### 숫자의 이유 드러내기

의미를 알 수 없는 숫자를 코드에 반복하지 않습니다.

```js
const NAVIGATION_HEIGHT_PX = 72;
```

가능하면 JavaScript 상수보다 CSS 디자인 토큰을 우선합니다.

### 변경 범위 제한

한 작업에서 기능 변경, 디자인 변경과 대규모 파일 정리를 동시에 하지 않습니다. 기획자가 변경 전후를 쉽게 비교할 수 있도록 커밋과 브랜치 목적을 하나로 유지합니다.

### 임시 코드 관리

- 사용하지 않는 코드를 주석 처리한 채 보관하지 않습니다. Git 기록에서 찾을 수 있으므로 삭제합니다.
- 임시 이미지나 복사 파일을 저장소에 남기지 않습니다.
- 임시 우회 처리가 필요하면 `TODO` 또는 `FIXME`에 제거 조건을 기록합니다.

## 좋은 주석과 피해야 할 주석

좋은 구조 주석은 기능의 역할을 설명합니다.

```jsx
{/* WHAT: 사용자가 프로젝트를 산업, 역할과 기술 기준으로 탐색하는 필터 영역 */}
<ProjectFilters />
```

좋은 결정 주석은 이유와 제약을 설명합니다.

```js
// WHY: 사용자의 현재 필터가 새로고침 후에도 유지되도록 URL query에 저장한다.
```

WHAT과 WHY 없이 코드를 그대로 읽어주는 주석은 작성하지 않습니다.

```js
// 비권장: 메뉴를 연다.
setIsMenuOpen(true);
```

## 코드 리뷰 확인 항목

- 페이지와 섹션의 위계가 한눈에 보이는가?
- 컴포넌트 이름이 기획 용어와 일치하는가?
- 페이지와 주요 섹션의 `WHAT`이 설명되어 있는가?
- 비직관적인 결정과 예외의 `WHY`가 설명되어 있는가?
- 디자인 시스템을 벗어난 값에 이유가 기록되어 있는가?
- 콘텐츠 수정이 레이아웃 코드와 분리되어 있는가?
- 로딩, 빈 화면, 오류와 모바일 상태를 확인했는가?
- 주석 처리된 오래된 코드와 임시 파일이 남아 있지 않은가?
