# 제품 개요

## 문서 기준과 읽는 법

- 확인 기준: `nana-park/breadme`의 `main` 커밋 [`3738e46`](https://github.com/nana-park/breadme/tree/3738e4620bb495ecfcd7ef589c91c2049ce0153a), 2026-10-05.
- 확인 방식: 공개 저장소의 실제 라우트, 렌더링 경로, 콘텐츠와 이벤트 처리 코드를 대조했다. 이 문서를 위해 방문자 조사, 성과 검증 또는 새 브라우저 검수를 수행한 것은 아니다.
- **현재 구현**은 코드에서 확인한 사실, **제안**은 다음 기획 검토를 위한 가설, **결정 필요**는 소유자의 선택 또는 추가 근거가 필요한 사항이다. 문서의 제안은 개발·콘텐츠 공개 승인이 아니다.
- 실제 배포 버전은 [배포 리비전](https://nana-park.github.io/breadme/deployment.json)으로 별도 확인한다. 이 문서의 코드 기준이 곧 현재 게시된 커밋이라는 뜻은 아니다.
- 페이지·CTA·콘텐츠 원본은 [라우트와 콘텐츠](routes-and-content.md), 협업 규칙은 [Ground Rules](../ground-rules/README.md)를 따른다.

## 1. 현재 구현: 어떤 제품인가

`breadme`는 Nahyun Park의 AI Product Manager 소개, 프로젝트 사례, 경력·역량, 연구·글·강의·수상을 탐색하는 영어 개인 포트폴리오 웹사이트다. 현재 Home은 `Designing AI Product Experiences Across Markets`라는 소개와 `View my work`, `Get in touch` 두 진입점을 제공한다. 이 표현은 **현재 화면의 포지셔닝**을 기록한 것이며, 문서 작성자가 별도로 경력이나 성과를 검증했다는 뜻은 아니다. [Home 문구](../../src/content/site/homeHero.ts), [Hero 구현](../../src/pages/home/HomeHero.tsx)

사이트는 React 클라이언트에서 화면을 렌더링하고 GitHub Pages에 정적 파일로 배포하도록 구성되어 있다. 콘텐츠를 보는 데 사이트 계정은 필요하지 않으며, 11개 기본 페이지와 연결된 프로젝트 상세 3개를 합쳐 14개 라우트가 있다. `Enjoy`는 라우트가 있으나 주 메뉴에는 없다. Articles의 18개 글은 별도 HTML 라우트가 아니라 하나의 페이지 안에서 해시 주소로 읽는다. [App](../../src/app/App.tsx), [라우트](../../src/config/originalRoutes.ts), [배포 설정](../../.github/workflows/deploy-pages.yml)

원본 `nana-park/Portfolio@8348159`를 React로 옮긴 콘텐츠가 대부분이며 Home Hero와 Articles 등은 별도 React 구성으로 관리한다. 현재 사이트는 서비스 사례를 설명하는 포트폴리오다. 상세 화면에 보이는 Voice IVR, Hopzie, Mentor AI의 제품 데모를 사이트 자체가 제공하는 실제 통화·커머스 생성·멘토링 자동화 서비스로 해석하지 않는다. [원본 페이지 구성](../../src/pages/original/README.md), [상세 인터랙션](../../src/shared/hooks/useOriginalDetailInteractions.ts)

| 측정·운영 | 저장소 기반 수정, 빌드·정적 라우트·배포 검사 구성 | 확인된 운영 대시보드, 앱 분석 이벤트·전환 추적, 목표치·기준선 |

검사 구성이 존재한다는 사실과 해당 리비전에서 검사가 통과했다는 사실은 다르다. 검수 결과는 [QA 안내](../qa/README.md)와 정확한 커밋의 CI를 확인한다. 현재 활성 코드에 앱 분석 도구/이벤트 전송은 확인되지 않았으며, 이는 호스팅 제공자나 외부 임베드의 처리가 전혀 없다는 의미는 아니다.

## 2. 현재 가능한 핵심 사용자 흐름

다음은 코드가 지원하는 경로다. 실제 방문자 행동 순위나 검증된 전환 퍼널은 아니다.

### 대표 경로: 소개 → 사례 → 연락 수단

1. Home에서 역할·소개 문구를 읽는다.
2. `View my work`로 Projects에 간다.
3. 목록·펼침 영역에서 관심 사례를 고르고 연결된 상세 페이지를 연다.
4. 사례 설명과 탭/미디어를 확인한다. `Back to Products`로 목록에 돌아갈 수 있다.
5. 공통 `CONTACT` 또는 Home의 `Get in touch`로 Contact에 간다.
6. 외부 프로필을 열거나 Footer의 메일 링크로 메일 앱을 연다. 사이트 안에서 실제 연락 발송 여부는 확인하지 못한다.

주의: Contact 본문의 이메일 표시 버튼과 `Copy URL`은 현재 복사 이벤트가 없다. 해당 버튼을 정상적인 연락 완료 단계로 정의하지 않는다. 자료 요청 역시 비활성 상태이므로 성공 전환으로 셀 수 없다. [CTA 상태](routes-and-content.md#2-공통-진입과-미완성-cta)

### 보조 경로

| 방문 목적 | 가능한 경로 | 사이트 안에서 확인 가능한 마지막 상태 |
| --- | --- | --- |
| 경력·판단 근거 확인 | About → Career / Qualified → Projects 또는 Research | 관련 콘텐츠와 연결 사례 열람 |
| 사고 과정·관심사 이해 | PROJECTS 하위 Articles → 목록 페이지 선택 → `Read Article` → `Back to List` | 같은 목록 페이지·스크롤·초점으로 복귀 |
| 연구 원문 확인 | Research → `Read Paper` / `Conference` | 외부 논문 페이지 또는 사이트에 배포된 PDF로 이동 |
| 강의·멘토링 사례 확인 | Lectures → 사진 캐러셀 → `View Workflow Detail` | Mentor AI 사례 상세 열람 |
| 지원 자료 획득 | Header의 Resume / Portfolio PDF | 준비 중 안내. 자료 수신·다운로드 성공 경로는 없음 |
| 한국어로 읽기 | Footer의 Korean / Articles의 `View Original (KR)` | 전자는 준비 중 안내, 후자는 외부 원문 이동 |

Articles의 목록 상태 보존은 같은 페이지가 마운트된 동안의 읽기/복귀 흐름이다. 새로고침 후 목록 쪽 번호까지 영구 복원하는 기능으로 설명하지 않는다.

## 3. 제안: 제품 목표와 사용자 가설

아래는 화면의 역할과 공개 문구에서 도출한 **검토용 제안**이다. 사용자 인터뷰·채용 성과·유입 데이터로 검증된 타깃은 없으며 우선순위도 승인 전이다.

### 제안하는 제품 목표

방문자가 짧은 탐색 안에 직무·강점을 이해하고, 관련 사례에서 본인의 역할과 판단 근거를 확인한 뒤, 사용할 수 있는 연락 수단을 찾게 한다.

| 사용자 가설 | 알고 싶은 것 | 현재 대응 페이지 | 검증 질문 |
| --- | --- | --- | --- |
| AI 제품 관련 채용 담당자·채용 의사결정자 | 어떤 역할을 맡았고 어떤 문제를 해결했는가 | Home, Projects, Career, Qualified | 첫 화면만 보고 직무와 차별점을 설명할 수 있는가? 상세에서 개인 기여와 팀 성과를 구분하는가? |
| 제품·연구 협업을 검토하는 사람 | 어떤 방식으로 문제를 정의하고 함께 일하는가 | 사례 상세, Research, Career | 필요한 근거를 찾고 협업 적합성을 판단할 수 있는가? |
| 동료 PM·강의·글 독자 | 어떤 관점과 경험을 공유하는가 | Articles, Lectures, Research | 기대한 글·강의 근거를 찾고 목록으로 돌아오기 쉬운가? |

어느 그룹을 1차 대상으로 삼을지, 한국어·영어 독자의 우선순위, 채용과 협업 중 핵심 목적은 결정 필요다. 제안된 사용자를 실제 이용자 구성으로 기재하거나 가상의 인터뷰·페르소나 세부사항을 추가하지 않는다.

### 제안하는 성공 기준

수치 목표와 측정 도구는 아직 정하지 않았다. 먼저 아래 질문으로 소규모 과업 관찰을 설계하고, 필요성과 개인정보 처리 범위를 승인한 뒤 계측을 검토한다.

| 확인할 결과 | 제안하는 검증 방법 | 현재 제약 |
| --- | --- | --- |
| 역할·가치 전달 | 첫 화면을 본 사람이 직무와 핵심 경험을 자신의 말로 설명하는지 관찰 | 참가자·통과 기준·시간 기준 미정 |
| 사례 발견과 이해 | 대표 사례를 찾고 문제·역할·결정을 설명하는 과업 | 관련 사례의 우선순위와 주장 검증 필요 |
| 연락 가능성 | 사용할 수 있는 연락 수단을 찾고 외부 이동까지 수행하는 과업 | 외부 클릭은 메시지 발송/채용 성과를 뜻하지 않음 |
| 글 읽기 연속성 | 목록 페이지 선택 → 글 읽기 → 복귀 시 위치를 잃지 않는지 관찰 | 조회·완독 계측 없음 |
| 정직한 상태 전달 | 자료/Korean 진입에서 준비 중임을 이해하는지 확인 | 전송을 약속하는 기존 문구와 비활성 상태 간 간극 검토 필요 |
| 콘텐츠 신뢰 | 중요한 역할·기간·수치·인용에 검토 가능한 근거와 승인 기록이 있는지 점검 | 원본 이관 테스트만으로 사실·공개 권한을 검증할 수 없음 |

분석 이벤트를 도입한다면 목적, 이벤트 정의, 분모·중복 처리, 보관 기간, 외부 제공자, 개인정보·동의 요구를 먼저 정한다. 이 문서는 도구 설치나 데이터 수집을 승인하지 않는다.

## 4. 결정 필요

아래는 제품 정의에 영향을 주는 질문의 요약이다. 우선순위·처리 상태는 [중앙 백로그](../backlog.md), 결정 기록은 [문서 유지보수](../maintenance.md)에서 관리한다. 이 표를 별도 승인 장부로 사용하지 않는다.

| 질문 | 결정 전에 필요한 근거 | 현재 안전한 해석 |
| --- | --- | --- |
| 첫 번째 방문자와 가장 중요한 다음 행동은 무엇인가? | 소유자의 채용·협업 목표와 탐색 과업 검토 | 여러 목적을 지원하는 포트폴리오로 기술 |
| 자료 기능은 직접 다운로드인가, 요청 메일인가, 보류인가? | 공개 가능한 파일, 전달 방식, 수집 필드·보관·삭제·실패 처리 | 준비 중. 실제 제공이나 성공을 약속하지 않음 |
| Korean은 전체 사이트 번역인가, 일부 콘텐츠 번역인가? | 언어별 범위·검토자·공식 명칭·미번역 처리 | 영어 활성, 한국어 원문은 외부 링크로 구분 |
| Enjoy를 탐색에 노출할 것인가? | 공개 의도·사진 권리·탐색 우선순위 | 메뉴 미노출이지만 직접 주소로 접근 가능; 비공개로 취급하지 않음 |
| Contact의 복사·자료 버튼을 어떻게 처리할 것인가? | 현재 미연결 상태 확인, 유지/수정/제거의 선택 | 작동하는 CTA와 분리해서 기록 |
| 프로젝트 성과·추천·로고·기사/연구 정보는 어떤 기준으로 승인할 것인가? | 공개 가능한 1차 근거, 시점·본인 기여 범위·공개 권한 | 화면의 주장과 검증된 사실을 구분 |
| 유입·연락 성과를 측정할 필요가 있는가? | 필요한 의사결정과 개인정보 처리 범위 | 측정치·성과 달성을 주장하지 않음 |

## 5. 유지보수 원칙

- 기능 설명을 바꿀 때 화면의 문구만 보지 않고 활성 렌더링·이벤트 연결까지 대조한다. `data-original-*` 문자열은 실행 가능한 핸들러라는 증거가 아니다.
- 경력·기간·성과 수치·공식 명칭·번역·공개 여부는 [콘텐츠 규칙](../ground-rules/10-content-and-localization.md)의 확인 대상이다. 근거 자료가 비공개라면 공개 저장소에 원문·비공개 링크·연락처를 복제하지 않는다.
- 이 문서의 목표·사용자·성공 기준은 명시적 결정 후 갱신한다. 결정 전에는 “제안” 표식을 유지한다.
- 라우트·주요 흐름·콘텐츠 위치 변경 시 [라우트와 콘텐츠](routes-and-content.md), 관련 페이지 README, 검수 범위를 같은 PR에서 맞춘다.
- 이 문서의 코드 확인일, 실제 CI 결과, 사용자 콘텐츠 승인, 배포 확인은 각각 따로 기록한다. 문서 검토·Draft PR 생성은 `main` 병합이나 공개 승인을 대신하지 않는다.
