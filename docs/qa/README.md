## 3. 실행 경로와 판정

Node 버전과 설치/에셋 준비는 [루트 실행 안내](../../README.md)를 따릅니다. 아래는 명령과 워크플로의 역할이며 이번 실행 결과가 아닙니다.

| 검사 | 실행/설정 | 판정 범위 |
| --- | --- | --- |
| 코드·단위·빌드 | `npm run check` | lint → typecheck → Vitest → build. 실제 화면 합격과 별개 |
| 일반 브라우저 회귀 | 빌드 후 `npm run test:e2e` | `tests/e2e`: 경로, Home, 메뉴, Articles, 스냅 등 |
| 모바일 읽기·상태 | 빌드 후 `npx playwright test --config=playwright.mobile-ui.config.ts` | 진단 캡처와 엄격 assertion을 구분. 캡처 생성 자체는 합격이 아님 |
| 원본 대비 엄격한 웹 비교 | 후보 빌드 후 `node scripts/prepare-desktop-unchanged.mjs`, `npx playwright test --config=playwright.desktop-unchanged.config.ts` | 고정 기준 `4f026a3` 대비 14경로 × 768/1440px × 첫 화면/Footer. 현재 전체 페이지 동등성 검사가 아님 |
| 정적 산출물 | `VITE_BASE_PATH=/breadme/ npm run build`, `VITE_BASE_PATH=/breadme/ npm run test:pages`, `npx playwright test --config=playwright.pages.config.ts` | 정적 HTML·base 경로와 실제 브라우저 검사를 각각 기록 |

- [`Foundation checks`](../../.github/workflows/ci.yml)와 [`Breadme production paths`](../../.github/workflows/pages-checks.yml)는 PR에 적용됩니다. 최종 SHA의 실제 실행 결과를 확인합니다.
- [`Mobile UI readability`](../../.github/workflows/mobile-ui-audit.yml)는 `feature/mobile-ui-readability` 또는 수동 실행 조건입니다. [`Home mobile layout review`](../../.github/workflows/home-layout-review.yml)도 경로·브랜치 조건이 있습니다. 새 브랜치에서 건너뛴 검사를 성공으로 세지 않습니다.
- Voice IVR의 원본 대조 진단에는 `continue-on-error`가 있습니다. 워크플로 단계 색상이나 상호작용 JSON의 중간 `statusBeforeRuntimeAssertion`보다 모든 hook을 포함한 최종 Playwright 결과를 우선합니다.
- [`Publish breadme`](../../.github/workflows/deploy-pages.yml)는 main push에 연결되어 있습니다. Draft PR·문서 검수·CI 통과는 병합/공개 승인이 아닙니다.

## 4. 화면과 사용자 흐름 확인표

### 화면 폭과 읽기

- 기본 비교는 모바일 390px, 태블릿 경계 768px, 데스크톱 1440px입니다. 작은 화면 320px와 767↔768px, 메뉴 1023↔1024px 경계를 추가합니다. 글자 줄바꿈 문제는 360/375/430px 등 실제 재현 폭을 포함합니다.
- Home 전체 반응형 변경은 320/390/767/768/1024/1025/1440px를 확인합니다. 모든 글을 모든 폭에서 검사했다는 식으로 범위를 넓혀 보고하지 않습니다.
- 가로 넘침, 글자/출처 잘림, 제목 위계, 이미지 자연 비율, 고정 헤더 가림, 마지막 CTA/연락 경로를 확인합니다. 의도된 가로 갤러리/표와 페이지 전체 넘침을 구분합니다.
- 200% 확인은 `root-font-200`, 계산값 기반 `synthetic-text-200`, 브라우저 자체 줌을 구분합니다. 합성 글자 확대 통과를 실제 줌·OS 글자 크기 통과로 표시하지 않습니다.

### 접근성과 환경

- 마우스 없이 핵심 흐름을 완료하고, 보이는 초점·버튼/링크 이름·제목 구조·비활성 상태·본문 바로가기를 확인합니다. Hover에서만 얻는 필수 정보가 없어야 합니다.
- 텍스트/배경 대비와 독립 조작 영역 44px 목표를 확인하고 범위·예외를 기록합니다. 자동 접근성 검사만으로 전체 적합성을 선언하지 않습니다.
- 일반 동작과 `prefers-reduced-motion`을 각각 확인합니다. reduced-motion 기본값인 진단 캡처로 일반 스냅 동작까지 확인했다고 하지 않습니다.
- 브라우저/OS·실제 기기 여부·viewport/DPR·글꼴/에셋 준비를 기록합니다. Chromium의 가상 viewport는 iOS Safari·Android 터치·Firefox·스크린리더 검수를 대신하지 않습니다.

## 5. 전체 UI 작업의 As-is / To-be 보고

모바일·웹 전체 디버깅에는 수정 코드와 **같은 브랜치**에 검토 문서를 만들고 README에서 연결합니다. 작은 단일 수정은 PR의 필요한 증거로 갈음할 수 있습니다. 과거 문서의 PNG를 새 결과로 바꾸지 않습니다.

각 문제는 다음 순서로 기록합니다.

1. **식별:** 결함/TC ID, 경로, CSS viewport 폭·높이, 화면 상태, 재현 절차
2. **기준:** As-is/To-be 각각의 불변 커밋, 캡처 실행/시각·브라우저·DPR·motion·글꼴 조건
3. **비교:** 동일 경로·폭·논리 상태의 전후 PNG. 부분 캡처·스크롤/세로 구도 차이·동적 영역 제외를 명시하고 대체 텍스트 제공
4. **판정:** 관찰 문제, 수정 내용/의도, 기대 결과, 실제 결과, 관련 TC와 최종 로그/CI 링크
5. **한계:** 미실행·실패·환경 제한·남은 승인 항목. PNG 생성과 수동 시각 검토 여부도 분리

첫 화면뿐 아니라 바뀐 본문·펼친 항목·메뉴/패널·Footer처럼 문제를 드러내는 상태를 포함합니다. 픽셀 비교는 같은 환경에서 수행하고, 동적 미디어를 제외했다면 위치·크기는 별도로 확인합니다. 작은 차이를 합격시키려고 허용치를 올리거나 기준 이미지를 덮어쓰지 않습니다. 의도된 디자인 변경은 승인과 새 기준의 이유를 남깁니다.

저장소에는 검토에 필요한 공개 화면과 요약만 남깁니다. 현재 CI artifact는 대체로 7일 보관이므로 장기 검토에 필요한 PNG는 검토 문서와 함께 보존하되, 전체 브라우저 로그·개인정보·인증 정보를 복사하지 않습니다.

## 6. 현재 남겨 두어야 할 증거 공백

- **엄격한 웹 비교:** 기록된 `ac0644` 실행은 25/28 사례 통과, 53/56 PNG 일치입니다. Hopzie 768px 첫 화면 5픽셀, AI Mentoring 768px 2픽셀, Hopzie 1440px 13픽셀 차이가 남았습니다. [해당 실행](https://github.com/nana-park/breadme/actions/runs/37272095126)과 [세부 기록](mobile-ui-desktop-evidence.md#후속-진단-실행-ac0644)을 역사 근거로 유지합니다. 이 수치는 현재 main의 검사 결과도, 해소 선언도 아닙니다.
- **외부 미디어 관련 실행 오류:** 같은 기록의 모바일 검사는 107/108이며 Voice IVR 오류가 후보와 변경 없는 기준에서 관찰됐습니다. 원인 단정·오류 무시 없이 재현 조건과 후보 stack을 확인할 과제가 남습니다.
- **AI Mentoring:** 선택적인 글자 역할 표식 2개는 여전히 보류입니다. 공통 메뉴/Footer 검수가 해당 본문 타이포그래피 개선 완료를 뜻하지 않습니다.
- **실제 환경:** 실제 기기·Safari/Firefox·스크린리더·브라우저 자체 200% 줌의 종합 검수 근거가 없습니다. 우선 핵심 사용자 흐름부터 환경과 결과를 남길 필요가 있습니다.
- **성능:** 에셋 무결성이나 빌드 성공을 로딩·메모리·레이아웃 안정성의 합격으로 보지 않습니다. 측정 조건과 개선 전후 수치가 있는 별도 과제입니다.

후속 과제의 완료는 정확한 SHA/실행/범위와 재현 가능한 결과로 판정합니다. 기존 실패는 원인과 재검사 근거가 생기기 전까지 해결로 바꾸지 않으며, 선택 개선이나 사용자 승인 대기는 기능 실패와 구분합니다.
